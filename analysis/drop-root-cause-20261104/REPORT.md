**The important new evidence**

The controller swap has already happened in the logs. The glasses enumerated on `1-5`, controller `0000:10:00.0`, at 10:58:15, replacing their old `5-2`, controller `0000:12:00.4`, connection. The same complete hub disappeared at **11:00:07.003, 11:00:30.507, and 11:01:04.723** while the same Luma XR session was running. This weakens a defect confined to the original port/controller. **Correction from the follow-up:** Razer1-1 is also on10:00.0, so this swap reintroduced controller sharing and was not an isolated-controller trial. The intervening old-port drops at10:46–10:57 happened while Razer was on the other controller, so sharing is not necessary for those failures. The logs alone cannot prove which individual disconnects were intentional; 10:57:44 immediately precedes the physical swap and should not be assumed spontaneous.

The original USB controller is not on the RX 7800 XT. The glasses' DP-2 output is on the discrete GPU at `03:00.0`; USB controller `12:00.4` shares a CPU PCI branch with the integrated GPU at `12:00.0`. These are different devices and branches. Moving USB preserved the glasses, cable, DP connection, tracking protocol, and software workload.

I independently parsed seven morning capture windows using the correct **48-byte usbmon API0 header**, checking every record to EOF. In all seven, the root port status is `00010100`: connection absent, connection-change set, power still reported on. There is no captured host request to switch off root-port power immediately before those losses. That power bit does not measure voltage at the glasses, and usbmon cannot reveal every controller-internal action.

At **10:46:04, 10:50:06, and 10:57:33**, there are **no control requests in the preceding 30 seconds**, apart from the root hub processing the disappearance in the final millisecond. Therefore an immediate camera suspend/resume, explicit control-transfer reset, or command burst is not necessary. The active stream is essentially the normal 1,000 IMU samples/second; no camera stream is needed for the failure. The 10:46:43 window includes the familiar short sample pause, but no failing completions in the final five-second window excluding teardown. A slow firmware failure triggered much earlier is not excluded.

Most cancellations are consequences of losing the link. The 10:57:44 capture has `-EPROTO` approximately 0.65 ms before the printed disconnect, unlike the earlier clean capture. Later re-enumeration also has descriptor timeouts at 10:46:49/10:47:05 and microphone setup failures after 11:00:07. These show recovery can be electrically/protocol-wise unhealthy; they do not establish why the first drop happened. Linux documents that a disconnect itself can produce such errors before the hub's removal message: [USB error codes](https://docs.kernel.org/driver-api/usb/error-codes.html).

**What the software audit found**

- The large `opens` number is misleadingly named. It counts daemon connection attempts, including waiting for a missing device. Going from opens149 to325 corresponds to **one** additional connection and **one** command. Opens357 remains unchanged through minutes of healthy streaming. It is not evidence of hundreds of USB resets or successful reopens.
- The new driver's actual ioctl allowlist permits claim/release, submit/reap, and cancellation. RESET, SET_CONFIGURATION, SET_INTERFACE, CLEAR_HALT and detach are rejected. It does perform normal interface claim/release and reconnect after failure. Both drivers still share IMU streaming and related device behavior, so replacing the SDK does not exclude a software-triggered firmware defect.
- The quiet shim is used only with the SDK driver. New Luma-driver failures exclude the shim and SDK-specific polling as necessary causes. The shim's reconnect delay intercepts SDK start, not all provider initialization; it never proved that the entire old initialization sequence was delayed.
- Readiness checks read state/logs. The controller can restart a failed startup or dead process and can restore display modes after a drop. I found no executable repository path that intentionally writes USB authorization, remove, bind/unbind or USB power settings, except the installed udev rule that keeps the hub and tracking device awake. Diagnostic commands printed in documentation are not runtime actions.
- The rolling recorder opens `/dev/usbmon5` read-only and copies files. It does not open `/dev/bus/usb` or reset devices. At the original cutoff it still watched/captured bus5. **Follow-up verified at11:12:** the recorder is now parameterized and running with `1 1-5`, so subsequent capture follows the correct bus. No new bus1 drop snapshot existed at that inspection; the11:00 failures cannot be reconstructed from a recorder started later. The incident hook sends a local notification; the inspected hook itself has no USB or display actions. Historical downstream automation is not a complete syscall audit.
- The incident report's “high confidence … cable, port or glasses rather than software” sentence is **hardcoded**, not an independent diagnosis. It should be corrected in a follow-up; it cannot be used as evidence against a software trigger.

The installed binary hashes match the historical consent records: Luma `66028d8c3fb0faa37067d7a26d7222980a2ec173fb9a2a4426134bc33f915db6`, renderer `83487371676880cd08e2fcb07179283923e15dcf49a1afc74605d338f6250713`. The controller imports `feature-placement-menu-integrate`; key tracking/display source files match this investigative checkout at `00c2328`. This is useful provenance, not proof of every opaque SDK operation.

**Host power, display and background programs**

The current hub and tracking device have `power/control=on`, are active, and report zero runtime-suspended time. The new USB controller also reports zero runtime-suspended time for this boot. The unused Sonix camera is different: `power/control=auto`, suspended. Thus “all autosuspend is disabled” is false, but parent autosuspend is poorly supported as the cause. No USB2 hardware-LPM control is exposed for these devices; inventing a `usb2_lpm_*` write or changing USB3 U1/U2 settings would not target an observed setting. Linux documents what these controls actually mean: [USB power management](https://docs.kernel.org/driver-api/usb/power-management.html).

There is a real configuration inconsistency: `/etc/modprobe.d/omarchy-usb-autosuspend.conf` says `options usbcore autosuspend=-1`, while live usbcore reports `2`. USB is built into this kernel (`CONFIG_USB=y`), and no corresponding boot parameter appears in `/proc/cmdline`. The file does not establish disabled autosuspend. Existing per-device rules still keep the parent and tracking device awake. Disabling the camera's own suspend remains a cheap narrow test, although three captured drops lack a recent camera-PM precursor.

Drops occur on both **7.2.8-9-omarchy** and **7.2.15-1-omarchy**. The latest kernel update therefore did not introduce the symptom. A shared kernel defect is still possible; no specific kernel regression was identified. There are no contemporaneous logged GPU resets, PCIe errors, xHCI-wide failures or system suspend events explaining the morning drops. Host Type-C/UCSI interfaces are absent; this adapter's negotiation is not exposed there.

XR requests 1920×1200 at120Hz on startup and can restore that mode after USB recovery/config reload. SBS mode changes follow an explicit flow. In the 10:38 event, the observed SBS change is later, not an immediate precursor. Later incidents show normal ~120Hz presentation immediately before loss, with zero capture failures. However, DRM/Hyprland incident times are polling observations, not precise DP hotplug edges. They cannot rule out a nearly simultaneous adapter/DP event. Historical GPU clocks, watts, temperature, CPU load, exact page-flip timing, and process device-open traces were not recorded. Current readings cannot reconstruct them. Depth inference can start while an SBS request is pending, so a 2D exit buffer alone does not prove no earlier depth workload.

No active fwupd, ModemManager, TLP or tuned service was found. Power Profiles and upower were running without a recurring logged precursor. The readable `/proc` snapshot found no camera, hidraw or USBFS owner; WirePlumber held the microphone's control device, not an active VITURE recording PCM. XR had already stopped, so this snapshot cannot establish historical opens. Root-process visibility is limited. Stock libmtp probes run during child enumeration; they are predominantly **after** a drop.

**Ranked next experiments**

These are proposals, not actions taken. Detailed copyable commands and restoration steps are in [EXPERIMENTS.md](EXPERIMENTS.md). Keep the physical connection fixed, record actual mode and driver state, and change one variable at a time. Prefer repeated matched runs; one quiet few-minute run proves little. Stop a trial once it has supplied a decisive failure rather than repeatedly provoking it.

1. **Separate tracking from XR at the same120Hz mode.** Compare plain display without tracking, tracking-only without XR, and XR with tracking. A tracking-only drop clears the renderer/controller/depth workload as necessary causes. XR failing with tracking genuinely absent points instead to display/GPU workload or host interactions. This is the most decisive software split.
2. **Compare XR60Hz versus120Hz**, automatic120Hz switching disabled and readback continuously verified. Starting at60Hz matters: the supervisor can restore120Hz after recovery. If only120Hz fails, concentrate on display/adapter/firmware/load; it would not by itself prove a bad cable.
3. **Keep just the Sonix camera awake**, leaving everything else identical. It is the one observed child power-management path not disabled. A repeat failure rules out camera autosuspend as necessary for that trial. Improvement must survive a restored-auto comparison.
4. **Capture the correct bus and exact ordering**, including kernel/DRM events, GPU telemetry and, with appropriate permissions, process/ioctl tracing. The old bus5 recorder misses new bus1 failures. No software test can conclusively distinguish power loss from firmware reset without additional observation.
5. If these do not isolate it, compare a second OS/kernel with the same minimal tracking workload, then a separately powered USB feed/cable comparison. The controller swap is already negative; do not repeat it as if untested. A powered hub changes topology as well as power, so improvement alone is not proof of undervoltage.

I recommend **no speculative driver reset/retry patch**. There are separate diagnostic issues (misleading incident attribution, ambiguous opens counter, stale readiness markers), but changing those will not establish or fix the initiating hub loss. The next useful result is a controlled tracking-versus-display experiment, not another assumption that software or hardware has already been cleared.
