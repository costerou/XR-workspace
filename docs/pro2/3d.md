# Pro 2 desktop 3D

The production Pro 2 route supports desktop depth through its own SBS scope: **3840×1080 at 60 Hz**. A panel session switches the glasses itself: turning a desktop's 3D on puts them in 3D, and turning the last 3D desktop off puts them back in 2D at **1920×1080 at 120 Hz** (see [Switched by the bridge](#switched-by-the-bridge)). **L1** still switches them by hand, and is what XR asks for if the switch cannot be sent. The [vendor guide](https://www.viture.com/academy/xr-glasses/pro-2) identifies L1 and full SBS at 3840×1080.

## Observed hardware

On November 8, 2026, with XR stopped, the user held L1. Hyprland reported:

| | Before | After |
|---|---|---|
| Output | DP-2 | DP-2 |
| Active mode | 1920×1080 at 120 Hz | 3840×1080 at 60 Hz |
| Scale | 2 | 2 |
| Advertised modes | 1080p at 60/90/120 Hz and fractional variants | Only 3840×1080 at 60 Hz |
| USB | `35ca:1301`, `VITURE PRO 2 XR Glasses`, Bus 001 Device 030 | Same identity and device number |

This establishes the physical button transition and host mode readback.

The installed production bundle `6b43dcb3d52c` then ran desktop depth on XR-1. Run `44cebef2ac87eafcbc90303e364f9f13` reported `phase=on`, `stereo=true`, `failed=false`, healthy tracking, and 59.998 Hz presentation. Read-only inspection of depth metadata showed a 420×266 output map at source sequence 3695, 15.29 ms old, with a 1.32 ms engine heartbeat age. No desktop pixels were saved.

An earlier startup ended when the tracking provider became unready; its windows recovered. A subsequent standalone bridge check ran 19.072 seconds with 2168 samples and no error, and the next production run stayed healthy with depth active. The first tracking interruption's cause is unconfirmed. The wearer then confirmed that depth works and holding L1 returns to 2D. They also reported edge artifacts at higher strength on both desktop borders/text and object outlines; that quality issue is separate from enabling SBS.

The subsequent [high-strength edge refinement](3d-edges.md) documents the rendering changes, before/after evidence, performance, and remaining limitations.

## Switched by the bridge

The bridge already owns VITURE's SDK for the session, so it takes the switch too: `RuntimeSession.set_display` writes one byte on the bridge's `--display-fd` pipe, and the bridge's owner thread passes it to `xr_device_provider_set_display_mode`. Only two values are accepted, both the SDK's public `VITURE_DISPLAY_MODE_*` constants: `0x32` (3840×1080 at 60 Hz, 3D) and `0x34` (1920×1080 at 120 Hz, 2D). Any other byte stops the bridge. `sbs.ButtonSbs` sends `0x32` from `enter()` and `0x34` from `leave()`, then follows the Hyprland readback exactly as it follows an L1 press. `leave()` runs only when no desktop is 3D any more (`ImmersiveRun._down`): on Stop, and when the last 3D desktop turns off.

Measured on November 8, 2026 (XR stopped, pinned SDK, scratch probe, glasses `35ca:1301` on Bus 001 Device 010 throughout):

| Call | DP-2 after | Advertised after | Pose stream open |
|---|---|---|---|
| `switch_dimension(1)` | 3840×1080 at 60 Hz, gone ~1.5 s | Only 3840×1080 at 60 Hz | No |
| `switch_dimension(0)` | 1920×1080 at **60** Hz | Only 1080p at 60 Hz | No |
| `set_display_mode(0x34)` | 1920×1080 at 120 Hz | Only 1080p at 120 Hz | No |
| `set_display_mode(0x32)` then `(0x34)` | 3D, then 1920×1080 at 120 Hz | As above | Yes: each call returned in ~4 ms, 390 poses per 6 s, largest gap 21 ms |

The SDK log shows `switch_dimension` is `set_display_mode(0x32/0x31)`. Its 2D is 60 Hz with nothing faster on offer, so Hyprland cannot bring 120 back; hence `0x34` directly. XRLinuxDriver v2.11.9 marks SBS unsupported on a Pro 2 and closes the IMU around the switch; neither was needed here. No USB disconnect was logged.

The Luma Ultra keeps the R1 prompt: our own driver has no known 3D command, and ids are never guessed ([display-control.md](../../spike/driver/docs/display-control.md)). A recovery after a crash has no bridge, so it asks for L1 as before.

## Installation and use

The depth runtime and an installed Pro 2 bundle containing its launcher are both required. From the checkout, after building the renderer and ownership plugin:

```sh
tools/depth_engine/setup.sh
python -m tools.xr_controller install --build build/release
systemctl --user restart viture-workspace-controller.service
```

The setup script installs the runtime and model under `~/.cache/viture-depth`; it needs network access and substantial disk space. Installation adds `xr-depth-engine` beside the bundle's renderer and includes its hash in the bundle manifest. Existing bundles remain available for rollback.

Start a new Pro 2 session after installation. Its confirmation includes the Pro 2 3D scope. Enable a desktop's 3D control and the glasses switch to 3D; L1 is asked for only if the switch cannot be sent. Glasses already in the supported SBS mode get no command. The adapter follows the mode the glasses advertise and verifies any compositor mode request by readback.

Turning the last desktop's depth off makes the rendering flat and switches the glasses back to 2D at 120 Hz. Holding L1 directly during active depth also stops depth and marks the display transition as expected. The adapter restores the previously observed 1080p refresh if the returned display still advertises it. A session started while already wide preserves the returned narrow mode when no earlier narrow refresh is known.

Only the observed 60 Hz SBS timing is enabled. Pro 2 never uses Luma's 1200p mode or R1 instructions. Production consent keeps `mode_switch=False` and carries the separately validated Pro 2 `sbs_mode`; bounded supervised tests retain their existing no-SBS scope.

Display handovers may restart the renderer while the same USB device and healthy tracking bridge remain. The bridge cannot reconnect across USB loss; a changed device or failed tracking health ends the session through normal recovery.
